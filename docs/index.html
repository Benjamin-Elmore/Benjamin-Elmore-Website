Case study: ARC firmware for ARSENAL

ARC is the C++ sensor firmware for ARSENAL, a custom ESP32-S3 board my robotics team is developing. I contribute to the firmware. This page covers the failure modes I reasoned about, how the design responds to them, and what has actually been checked so far.

The problem

The CBU1 VEX U team is developing ARSENAL, a custom ESP32-S3 board designed to connect external sensors to a VEX V5 Brain. ARC is the C++ firmware that runs on it. The ARSENAL board and the existing sensor code are the team’s work.

My role

I’m a firmware contributor. I work with electrical and computer engineers on device interfaces. My part:

  • Moved I²C communication toward the ESP-IDF master API.
  • Added optical sensor register access and position decoding.
  • Worked on mutex-protected bus access.
  • Worked on UART and RS-485 diagnostics.
  • Committed implementation and debugging work.

Engineering decisions

  1. Evolve the sensor abstraction

    Failure mode
    If each sensor type gets its own code, the acquisition logic is copied from sensor to sensor. Early work used a sensor base class with an optical specialization.
    Design response
    The testing design uses configurable setup and read callbacks plus preconfiguration, so one acquisition path serves different sensor types. Optical register reads, writes and offset handling are the concrete example.

  2. Give the bus a clear owner

    Failure mode
    The mux is shared. Another task can switch its channel between the channel select and the sensor transaction that depends on it.
    Design response
    A templated I2CBus<N> owns device registrations, register operations, mux selection and a bus mutex. The channel select and its matching transaction run under the same lock. A noncopyable lock guard scopes the lock, and later work checks for failed acquisition.

  3. Separate acquisition from requests

    Failure mode
    A request from the controller should not have to run a sensor-specific I²C sequence itself.
    Design response
    The architecture gives acquisition and communication separate tasks. The acquisition side selects the channel and stores readings. The communication side uses a sensor-ID registry and a small readings and offset interface.

  4. Isolate bring-up failures

    Failure mode
    A transceiver problem can hide sensor bugs, and a sensor problem can look like a communication bug.
    Design response
    The current entry point starts the RS-485 path with an empty sensor registry, so I can debug communication with the sensor hardware out of the loop. UART startup and status reporting, plus I²C error logging, help narrow a failure to one layer.
