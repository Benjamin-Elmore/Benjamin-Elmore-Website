Case study: ARC firmware for ARSENAL

I contribute to ARC, the C++ sensor firmware for my robotics team’s custom board. This case study covers the failure modes I reasoned about, how the design responds to them, and what has been checked so far.

The problem

The CBU1 VEX U team is developing ARSENAL, a custom ESP32-S3 board designed to connect external sensors to a VEX V5 Brain. ARC is the C++ sensor firmware written for it. The ARSENAL board is the team’s work. The existing sensor code came from the team and from earlier reference code.

My role

I’m a firmware contributor. I work with electrical and computer engineers on device interfaces. My part:

  • Prototyped the sensor abstraction.
  • Moved I²C communication toward the ESP-IDF master API.
  • Added optical sensor register access and position decoding.
  • Worked on mutex-protected bus access.
  • Worked on UART and RS-485 diagnostics.
  • Added explicit error propagation.

Engineering decisions

  1. Evolve the sensor abstraction

    Failure mode
    If each sensor type gets its own code, the acquisition logic gets copied from sensor to sensor.
    Design response
    Early work used a sensor base class with an optical specialization. The later design moved to configurable setup and read callbacks plus preconfiguration, so one acquisition path can serve different sensor types. Optical register reads, writes and offset handling are the concrete example.

  2. Give the bus a clear owner

    Failure mode
    The mux is shared. Another task can switch its channel between the channel select and the sensor transaction that depends on it.
    Design response
    A templated I2CBus<N> owns device registrations, register operations, mux selection and a bus mutex. The channel select and its matching transaction run under the same lock. A noncopyable lock guard scopes the lock, and later work checks whether taking the lock failed.

  3. Separate acquisition from requests

    Failure mode
    A request from the controller should not have to run a sensor-specific I²C sequence itself.
    Design response
    The architecture gives acquisition and communication separate tasks. The acquisition side selects the channel and stores readings. The communication side uses a sensor-ID registry and a small readings and offset interface.

  4. Isolate bring-up failures

    Failure mode
    A transceiver problem can hide sensor bugs, and a sensor problem can look like a communication bug.
    Design response
    The current entry point starts the RS-485 path with an empty sensor registry, so I can debug communication with the sensor hardware out of the loop. UART startup and status reporting, plus I²C error logging, help narrow a failure to one layer.
