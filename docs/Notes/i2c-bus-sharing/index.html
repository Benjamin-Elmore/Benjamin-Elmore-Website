Note

Sharing one I²C bus between FreeRTOS sensor tasks

November 10, 2026 · ARC, CBU1 VEX U Robotics

Note

ARC runs one FreeRTOS task per sensor, and several sensors can sit behind I²C multiplexers on one bus. Reading a sensor behind a multiplexer takes two transactions: select the channel, then talk to the sensor. If another task selects a different channel between those two steps, the read goes to the wrong device or fails.

A mutex per multiplexer does not fix this. Two tasks can hold different multiplexer locks and still share the same upstream bus, so the whole bus needs one lock, held across the select and the transfer.

Where the lock lives also matters. An early version took the lock only around the read function, leaving setup and loop callbacks outside it, so a callback that touched I²C could interleave with another task's transaction. In the current design the I2CBus class owns the bus and its multiplexers, and every register read or write takes the held lock as an argument and is refused without it.

The lock is a small RAII class, LockGuard. It releases the mutex when it goes out of scope, and only if it actually took the mutex, so a failed acquisition cannot release another task's lock.

Scope: this is a design note. The full sensor-to-V5 path has not been run on hardware.

Part of the ARC case study. Described at the CPPDev branch, commit 49d54a0.
